# 全文独有候选的虚假向量分数：最小复现

## 1. Mock 输入

直接 mock 两路数据库查询返回值，不需要数据库、embedding 服务或 LLM。分数是构造的测试输入，不代表线上全文分数分布。

| 记忆 | 向量查询返回 | 全文查询返回 | 含义 |
|---|---:|---:|---|
| V | 0.8 | 无 | 仅向量召回 |
| B | 0.6 | 1.0 | 两路均召回 |
| F | 无 | 2.0 | 仅全文召回 |

所有记忆设 `observed_at=None`、`initial_confidence=1`，无反馈。因此时间分为 0，置信度分为 1，不触发低置信度过滤。取 Top 2，无同分情况。

采用当前权重：`总分 = 0.3×向量分 + 0.2×关键词分 + 0.2×时间分 + 0.3×置信度分`；关键词分为 `raw_ft / (raw_ft + 1)`（raw_ft > 0 时）。

## 2. 原实现怎么样

`memoria/crates/memoria-storage/src/store.rs` 中，向量查询把 `1/(1+max(distance,0))` 写入 `Memory.retrieval_score`；全文查询把原始 `ft_score` 写入同一字段。

混合检索先保存 `ft_map`，再以向量结果为基础合并全文结果；相同 ID 保留向量对象，全文独有对象直接追加：

```rust
let mut candidates = vec_results;
for m in ft_results {
    if seen.insert(m.memory_id.clone()) {
        candidates.push(m);
    }
}
// 后面的统一评分循环：
let vec_score = m.retrieval_score.unwrap_or(0.0);
```

合并后 V 的字段值是 0.8、B 是 0.6、F 是 2.0。最后一行把三者都解释为向量分，F 的全文分因此同时参与了向量项和关键词项。

## 3. 为什么会这样

根因是合并后仍把来源不同的字段值当成同一种分数。`retrieval_score` 在不同阶段分别表示向量分、全文分和最终融合分；字段复用本身未必错误，但读取时必须知道分数来源。这里只单独保留了全文来源分数，没有独立保存向量来源分数。

`unwrap_or(0.0)` 无法兜底：F 的字段不是 None，而是 `Some(2.0)`。只改接口名或字段名也不会改变这个值的来源与计算结果。

全文独有候选是可达情况：全文查询不要求 embedding 非空，而向量查询要求；即使有 embedding，也可能未进入有限大小的向量候选集合。

## 4. 实际复现结果与影响

| 记忆 | 原实现向量项输入 | 修正后向量项输入 | 关键词分 | 原总分 | 修正后总分 |
|---|---:|---:|---:|---:|---:|
| V | 0.8 | 0.8 | 0 | 0.5400 | 0.5400 |
| B | 0.6 | 0.6 | 0.5 | 0.5800 | 0.5800 |
| F | **2.0** | **0** | 0.6667 | **1.0333** | **0.4333** |

F 原总分为 `0.3×2 + 0.2×(2/3) + 0.3 = 1.0333`；正确按已有召回证据计算应为 `0 + 0.2×(2/3) + 0.3 = 0.4333`。

这里的 0 表示“没有从向量召回得到分数，因此不贡献向量项”，不代表 F 的真实语义相似度为零。

- **排序和上下文被改变：** 原实现 Top 2 为 F、B；修正后为 B、V。F 靠误加的分数挤掉了 V。真实回答质量是否受损取决于内容，需要 benchmark 测量，不能由此样例量化。
- **权重失真：** 在无反馈条件下，全文独有候选额外获得 `0.3×raw_ft`。任何正全文分都会产生额外加分，并非只有全文分大于 1 才出错。本例超过 1 是现象，分数来源错配才是根因。
- **解释信息失真：** 当前 `score_breakdown` 同样记录错误的向量分；排查检索质量时，会误以为 F 得到了很强的向量匹配。

## 5. 建议的最小修正

在移动 `vec_results` 前，与现有 `ft_map` 对称地保存向量来源分数：

```rust
let vec_map: std::collections::HashMap<String, f64> = vec_results
    .iter()
    .filter_map(|m| m.retrieval_score.map(|s| (m.memory_id.clone(), s)))
    .collect();
// 评分循环用这一行替换对候选 retrieval_score 的直接读取：
let vec_score = vec_map.get(&m.memory_id).copied().unwrap_or(0.0);
```

无需改公共接口、数据库结构、权重或增加查询。这里只给出修正示意，没有修改产品实现。

## 6. 运行与验收边界

在仓库根目录执行：

```sh
rustc --test docs/examples/hybrid-score-mock.rs -o /tmp/hybrid-score-mock
/tmp/hybrid-score-mock --nocapture
```

这个标准库 mock 保留原实现的合并、分数读取和相关评分公式，并对照 vec_map 修正后的计算。断言验证 F 的错误向量分为 2、修正后为 0，V/B 总分不变，以及两种 Top 2 顺序。

**测试通过表示成功复现问题及验证修正思路，不表示产品已经修好。** 它不调用生产函数，不验证数据库 SQL、embedding 或完整检索链路；正式 PR 仍应在生产混合检索路径补上同样输入语义的回归测试，确保改前失败、改后通过。
